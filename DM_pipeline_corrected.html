2. Plain-English Walkthrough: The Entire Process Explained Simply

The Real-World Problem: What Are We Trying to Solve?

Imagine an IT Helpdesk for a major enterprise. Every time an employee has an issue (laptop broken, email locked, server down, database crashed), they submit a support ticket.

Every ticket comes with a company commitment called an SLA (Service Level Agreement): "We promise to fix this issue within X hours."

The Core Problem:

Out of ~25,000 historical tickets, 36.6% (over 9,100 tickets) miss their SLA deadline!

Why Tickets Fail:

1) Ping-pong bouncing between 79 support teams. 2) Waiting room traps (stuck in Awaiting Vendor/User). 3) Reactive triage (noticing delays only after the deadline has breached).

The 5 Steps of the Solution

Step 1: Clean & Split Data (Dual Streams)

We clean dirty '?' values and split data into two views: Stream A (The Journey)—the timeline of updates, and Stream B (The Passport)—the ticket's Day-1 attributes (caller, category, priority).

Step 2: Process Mining (Spotting Bottlenecks)

We watch how tickets actually travel between teams. We detect ping-pong loops (bouncing between teams) and measure idle dwell hours in holding states to create behavioral scores for every ticket.

Step 3: Profiling & Workload Clustering

We flag extreme "nightmare" tickets (e.g. 500+ hours, 10 reassignments) for deep root-cause inspection—we never delete them! Then we cluster normal tickets into 3 workloads: Quick Desk, Cross-Tier Infra, and Vendor-Dependent.

Step 4: Root-Cause Rules (Plain-English Laws)

FP-Growth scans past failures to produce transparent IF-THEN rules: "IF Category = Database AND Reassignments > 2 ⇒ SLA Breach Probability = 88%." Managers can easily understand and trust these rules.

Step 5: Real-Time AI Prediction (LightGBM)

The moment a new ticket arrives, the AI scores its breach risk (0–100%) and recommends the optimal assignment group, bypassing intermediate triage hops before delays can accumulate.

3. Flaws in the Original Pipeline vs. Technical Rectifications

Pipeline Component Original Pipeline Flaw (DM pipeline.html) Methodological Rectification
Outlier Handling Fatal Flaw
Isolation Forest strips out "extreme statistical anomalies" before process and rule mining. In ITSM, the worst outliers are tickets with 10+ reassignments, massive delays, or severe SLA breaches. Discarding them deletes the exact failure cases you need to diagnose! 		Retain & Profile
Isolation Forest / LOF profiles deviant and pathological tickets for a dedicated Pathological Incident Audit, but they are retained in the dataset so models can learn the root causes of failure.
Data Granularity Unit Mismatch
Treats the event log as a flat table for K-Means clustering. An incident has between 2 to 40+ update rows. Clustering raw event rows scatters lifecycle events of the same ticket across different clusters. 		Dual-Stream Architecture
Stream A preserves the temporal event trace sequence for Process Mining. Stream B aggregates attributes to the Case level (1 row = 1 ticket) for ML and Clustering.
Execution Ordering Inverted Order
Runs clustering before process mining. This blinds clustering to crucial workflow metrics (ping-pong factor, dwell time in waiting states, rework cycles). 		Process Mining First
Process Mining executes first on the global event traces. It extracts quantitative behavioral features per ticket, which then feed directly into downstream clustering and predictive models.
Rule Mining Bridge Incompatible Input
Attempts to feed Apriori/FP-growth symbolic text rules into a "Regression Model" to predict SLA breaches. ML models train on numerical feature matrices, not text rule strings. 		Decoupled Dual Intelligence
Predictive ML uses Gradient Boosted Trees (LightGBM/XGBoost) for Binary Classification of SLA breach risk. Association rules provide human-readable symbolic explanations and operational guardrails.
Temporal Data Leakage Future Leakage
Scores live incoming tickets using features that only exist after resolution or closure (e.g., resolved_at, resolved_by, closed_code, cumulative reassignment_count). 		Multi-Stage Safeguards
Strict temporal separation: Stage 1 (Intake Model at t=0) uses strictly features known at ticket creation; Stage 2 (In-Flight Dynamic Model at t=k) updates risk scores at state milestones.

4. Phase-by-Phase Technical Specifications

Phase 1: Dual-Stream Data Hygiene & Feature Ingestion

  • Data Hygiene: Convert '?' characters into standard NaN. Remove corrupted state values (e.g., incident_state == '-100'). Convert ultra-sparse columns (>98% missing: cmdb_ci, problem_id, rfc, vendor, caused_by) into binary indicator flags (e.g., has_problem_id = True/False).
  • Timestamp Parsing: Parse date strings with format %d/%m/%Y %H:%M and sort events chronologically by sys_updated_at within each incident number.
  • Dual Representation:
    • Stream A (Event Trace View): Case ID (number), Activity (incident_state, assignment_group), Timestamp (sys_updated_at), Resource (assigned_to).
    • Stream B (Case Intake Matrix): Intake attributes known at t=0: Category, Subcategory, Location, Caller ID, Contact Type, Priority, Urgency, Impact, Open Hour of Day, Day of Week.

Phase 2: Global Process Mining & Workflow Bottlenecks

  • Trace Mining: Run Directly-Follows Graphs (DFG) and Heuristics/Inductive Miners across all 24,918 case traces using PM4Py.
  • Bottleneck Identification:
    • Ping-Pong Loops: Automatically detect cyclic reassignment patterns between groups (e.g., Group 70 → Group 24 → Group 70).
    • Dwell Time Analysis: Measure exact time spent in non-working states (Awaiting User Info, Awaiting Vendor, Awaiting Problem).
  • Feature Engineering Output: Generate quantitative behavioral features per ticket: handoff_count, is_ping_pong_loop, dwell_awaiting_user_hrs, unique_groups_involved.

Phase 3: Case Feature Integration, Anomaly Profiling & Workload Clustering

  • Feature Store Fusion: Join static intake attributes (Stream B) with trace-engineered process features (Phase 2) to build a unified Case Feature Store (1 row = 1 incident ticket).
  • Anomaly Profiling (Isolation Forest / LOF): Detect and flag extreme pathological tickets (resolution time > 500 hours or > 5 reassignments). These are profiled for deep root-cause inspection, never discarded.
  • Workload Segmentation (K-Prototypes / HDBSCAN): Cluster tickets using mixed numerical and categorical attributes to identify distinct operational workloads:
    • Archetype 1 (Fast-Track): Low complexity, single-touch password/desktop resets (< 2h).
    • Archetype 2 (Cross-Tier Infra): High complexity, multi-group server/network issues requiring cross-department handoffs.
    • Archetype 3 (External Blocked): Tickets with high dwell time in vendor/user awaiting states.

Phase 4: Root-Cause Pattern & Association Rule Mining

  • Feature Discretization: Bin numerical metrics into categorical intervals: Handoffs: [0-1, 2-3, >3], Wait_Dwell: [Low, High], Resolution: [<24h, 24-168h, >168h].
  • FP-Growth Algorithm: Mine frequent itemsets and extract association rules filtered specifically for target failure consequents:
    • Antecedent ⇒ {made_sla = False}
    • Antecedent ⇒ {is_ping_pong = True}
  • Knowledge Base Output: Symbolic, human-interpretable rules with Confidence > 70% and Lift > 1.5 (e.g., IF {Category 40, Priority Moderate, Handoffs > 2} ⇒ {SLA Breach Probability: 88%, Lift: 2.3}).

Phase 5: Multi-Stage Predictive Analytics & Decision Support

  • Strict Temporal Validation: Chronological train/test split (train on earlier months, test on subsequent months) to ensure zero lookahead bias.
  • Supervised Ensemble (LightGBM / XGBoost):
    1. Stage 1 — Intake SLA Breach Classifier (t=0): Real-time risk scoring using only intake attributes.
    2. Stage 2 — Dynamic In-Flight Re-Scorer (t=k): Dynamic risk adjustment as tickets undergo reassignments or enter wait states.
    3. Stage 3 — Smart Routing Recommender: Multi-class model predicting the correct assignment group at intake, eliminating intermediate triage hops.
  • Operational Decision Support Dashboard: Real-time dispatcher UI displaying live risk queues, SHAP feature importance bars, and matching Phase 4 rule warnings.
